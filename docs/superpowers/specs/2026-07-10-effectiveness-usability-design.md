# 有效性验证闭环 + 使用者动线 设计（2026-07-10）

## 背景与问题

以真实使用者视角审查产品后确认的三个核心问题：

1. **有效性无法被证明**：复盘页只有绝对收益口径。实测近 7 个交易日（470 条留痕）三池 T+1 胜率 31–36%、平均 -1.8~-2.4%，但同期全市场中位 T+1 最低到 -2.96%（7-06，胜率 12%）——用户分不清「策略差」还是「大盘跌」。专业产品（果仁网/qlib/InStock）全部用超额收益口径。
2. **统计被脏数据污染**：日线同步缺口（如 7-09 仅 23 只股票有 bar）会让 T+N 统计建立在残缺截面上，且页面无任何提示。
3. **实盘留痕积累太慢**：7 天样本无法支撑任何结论；本地已有 5525 只 × 多年日线，可以直接做 point-in-time 历史回放验证。

使用者动线缺口：信号不可解释（为什么入选？这个信号历史表现如何？）；只管买不管卖；选完票之后没有跟踪工具（自选股无盈亏概念）。

## 目标

- 每个选股池的有效性可以用「超额收益」口径被验证或证伪，回放 + 实盘留痕双轨。
- 数据质量问题对用户可见、可自愈，不污染统计。
- 从「看到票」到「持有跟踪、知道何时卖」动线完整。

## 非目标

- 不承诺胜率；不做实盘交易接口；不做自然语言选股（P2，另立项）；不改现有选股规则本身（回放结果出来后另行迭代）。

## 批次设计

### 批次 1：复盘基准超额 + 统计防污染

- `local_store.evaluate_picks`：
  - 新增市场基准：按 (pick_date, horizon) 计算全市场（amount>0 截面）中位收益，模块级缓存（同一评估内一次扫描构建收盘矩阵，避免逐条查询）。
  - 每条 item 增加 `excess_t1/t3/t5 = ret_tN − market_median_tN`。
  - 池统计增加 `excess_win_rate`（超额>0 占比）、`avg_excess`。
  - **覆盖率守卫**：T+N 目标交易日的 bar 覆盖数 < 当日全市场活跃股 60% 时，该 horizon 记为未就绪（返回 null），不进统计。
- API `GET /api/quant/picks/stats` 透传新字段，接口形状向后兼容（只加字段）。
- 前端 Review 页：池卡片加「超额胜率 / 平均超额」，明细表加超额列（红涨绿跌染色），口径说明更新。
- 测试：扩展 `tests/test_picks_history.py`（构造已知市场截面验证超额计算与覆盖率守卫）。

### 批次 2：数据新鲜度守卫

- `GET /api/quant/data-health`：最新交易日、日线覆盖 N/总数、近 10 个交易日逐日覆盖率、状态分级（ok ≥95% / warn ≥60% / bad <60%）。轻量线程池执行。
- 覆盖率 < 95% 时允许触发增量补齐（复用现有 sync_service，防重入 + 冷却）。
- 前端：Review 页与智能选股页顶部新鲜度徽章（绿/黄/红 + 「日线截至 X · 覆盖 N/M」），bad 时提示「统计已自动排除残缺日」。

### 批次 3：历史回放验证（核心）

- 新模块 `quantcore/quant/replay.py`：
  - **pattern 池**：本地日线截断到 as_of 日，跑同一套形态分析（严格 point-in-time）。
  - **smart 池**：评分输入用日线近似重建（pct_chg=close/prev−1、amount=当日 bar、volume_ratio=vol/MA5(vol)、turnover 缺失取 0、MA20/anti_chase 由截断后的 bars 计算），critic/实时融合层跳过；结果标注「近似回放」。
  - 回放窗口默认 12 个月、每个交易日取 top-N（与线上池同 N），记 T+5 收益与全市场中位基准。
  - 结果落 `replay_results` 表（run_id, pool, as_of_date, symbol, rank, score, ret_t5, excess_t5），run 级汇总存 `replay_runs`。
- API：`POST /api/quant/replay/run`（后台任务 + 进度查询，防重入）、`GET /api/quant/replay/results`（月度胜率/超额、累计超额曲线、总体汇总）。
- 前端 Review 页新 tab「历史回放」：累计超额曲线（ECharts）+ 月度表 + 近似口径免责说明。
- **交付物包含一次真实回放运行的结果与结论写入本 spec 同目录的验证报告。**

### 批次 4：入选理由卡

- 后端：`GET /api/quant/signal-stats?pool=&pattern=`——按池/形态聚合留痕 + 回放的历史 T+5 超额胜率与样本数。
- 前端：智能/形态选股表行内「为什么入选」入口 → 抽屉：因子分解（已有 factors）、reasons、trade_plan（已有）、该信号历史表现（双口径，样本数标注）。

### 批次 5：模拟组合 + 卖出信号

- 表：`portfolio_positions / portfolio_trades / portfolio_nav`（user_id 维度；结算逻辑参考 arena.py：先卖后买、整手、A 股交易成本）。
- API：加入（按最新价/收盘价买入指定金额，默认 1 万/笔）、卖出、持仓列表、NAV 序列。
- 收盘结算：挂现有 15:40 cron（交易日守卫已有），当日收盘价结算 NAV，同时算沪深300 对比。
- 卖出信号：持仓逐日检查——收盘跌破 MA20 / 自买入价回撤超 8% / 持有超 10 个交易日未创新高——命中则持仓行打「建议卖出」徽章 + 原因。
- 前端：选股列表行「+组合」按钮；`/portfolio` 页（持仓表 + 盈亏 + NAV vs 沪深300 曲线 + 卖出信号徽章）。

## 数据流与错误处理共性约定

- 涉及外部数据的 float 一律 `x == x` 判 NaN 后再入 JSON（历史教训：NaN 序列化 500）。
- 当日盘中计算必须传实时快照兜底（收盘前本地日线未同步）。
- cron 挂 `_is_trading_day_now()` 守卫；重任务走后台线程，轻接口走 `_light_executor`。
- 回放/补齐等长任务：防重入 + 进度可查 + 失败可重跑（幂等）。

## 验证标准

- 每批次：pytest 全绿 + `vue-tsc`/vite 构建通过 + headless Playwright 实机巡检该批次页面（真实数据）。
- 批次 3 额外交付：真实回放跑通 ≥12 个月，输出各池「有效/无效/近似口径存疑」结论报告。
